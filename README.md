# 炸带 ZhaDai

给原版泰拉瑞亚（1.4.5.8）算一份**用雷管炸出隔离带**的施工方案，并且可以接管游戏自动施工。

和常见的隔离带分析器不同，这里算出来的不是一条竖带，而是**贴着感染前沿轮廓走的斜带**：宽的只是该宽的地方，能斜着走就斜着走，最后把腐化/猩红/神圣关在尽可能小的一片区域里。

- 规划器只读存档，不改世界、角色、地图文件。
- 接管执行是可逆 IL 注入，装之前先备份 `Terraria.exe` 并记哈希，随时可以还原。
- 前端是一个亮色、无边框、几乎只有数字的小窗口。

```
规划 → 一份施工方案（JSON / 交互地图 / 游戏内施工文件） → 接管执行
```

## 快速开始

```powershell
# 只看存档和感染源概况
dotnet run --project src/ZhaDai.Cli -- info "存档.wld"

# 出一份方案：控制台报告 + JSON + 交互地图
dotnet run --project src/ZhaDai.Cli -- plan "存档.wld" `
    --json=plan.json --html=plan.html --zplan=plan.zplan

# 算完直接把施工文件和运行配置放进游戏目录（这一步仍然不碰 Terraria.exe）
dotnet run --project src/ZhaDai.Cli -- arm "存档.wld"
```

`arm` 会在 `<泰拉瑞亚目录>\ZhaDai\` 下写出两个文件：`active.zplan`（施工文件）和
`run.cfg`（运行配置，默认 `enabled=0`）。有隔离段没过泛洪复核时它会**拒绝写出**，
必须显式加 `--force` 才写——「有段没封住就别照着炸」应该是默认行为，而不是一句提示。

在一张 8400×2400 的肉前存档上的真实输出（存档每玩一次这些数字都会变，下面是某一次的实际结果）：

```
世界：草剑挥打（格式 326，8400x2400）
难度：肉前
感染源：邪恶 97152 格，神圣 0 格；可感染物块 5234598 格
隔离段：822 段（其中混合段 0）
封带物块：30474 格；雷管：10346 发（约 105 组）
封住的感染物块：97152 格（占全部可感染物块 1.856%）
爆破总摧毁：1308130 格（其中炸不掉而留存 1818 格）
封带泛洪复核：全部封住
预计施工：约 1896.8 分钟
危险物块：岩浆 0、水 18422、陷阱 16、墓碑 0、爆炸物 0
带草的前沿物块（会长藤蔓）：1948 格
```

同一张存档加 `--vine-reach=0`：封带 19389 格、雷管 2936 发、封住 388365 格，
复核仍然全封住，但上面那 1948 格带草物块下方的空气通道就没有封，方案会在提示里明确警告这一点 —— 
省下的 3.5 倍炸药是拿「藤蔓有一天会把感染带下去」换来的。

`exit code` 是给脚本用的：`0` 全部封住，`2` 有段没封住（这时千万别照着施工），`1` 用法错。

### 常用选项

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--clearance=<格>` | 6 | 封带厚度。不得小于 4（3 格扩散 + 1 格余量）。调到 4 最省炸药。 |
| `--vine-reach=<格>` | 13 | 藤蔓能顺着空气向下把感染带多远。设 0 只按普通三格扩散封带，炸药省约 3.7 倍，但带草的陡坡前沿不保险。 |
| `--merge-gap=<格>` | 3 | 多近的两片感染源并成一段封。调大省炸药，代价是关进去的区域更大。 |
| `--also-rect=x0,y0,x1,y1` | — | 额外把一块矩形当感染源（可重复），用来把肉前 V 字预测范围也一起封进去。 |
| `--protect=<级别>` | strict | 误伤控制。`strict`：结构和玩家建材（木板/砖/玻璃等）都不炸，那几格改由镐子挖；`structures`：只保护箱子、门、家具、平台这类结构，普通建材可以让路；`none`：不保护，按最少雷管摆位，误伤只做统计。 |
| `--no-plug` | 关 | 不用封堵块顶掉藤蔓竖井（默认用 1 块木头换掉 13 格竖井）。 |
| `--plug-item=<物品id>` | 9 | 封堵用的物品，默认木材。 |
| `--protect-buffer=<格>` | 1 | 保护范围外再留几格余量（0..3）。 |
| `--pick=<镐力>` | 100 | 规划时假设的镐力（100% = 熔岩镐，210% = 锯镐）。它决定「这格挖不挖得动」，也写进施工文件供接管前盘点。 |

## 镐子也是施工手段，不只是炸药

雷管炸不掉不等于处理不掉。这一版把两件工具分开算：

- **每一格封带都会先判一次**：雷管能炸 / 只能挖 / 两样都不行。判据不是猜的，是从 `Player.GetPickaxeDamage` 抄下来的镐力闸门（黑檀石 65%、地牢砖 100%、钴矿 100%、秘银 110%、精金 150%、叶绿 200%、神庙砖 210%），以及 `WorldGen.CanKillTile` 的例外（`wall 350` 保护其上方格子、锁住的门、树、箱子）。
- **「两样都处理不掉」会被点名**：祭坛（26）不是镐子的目标，神庙砖要 210% 镐力。这类格子会被从封带里剔除、如实报出来，复核也会随之变成「未封住」，`arm` 直接拒绝写施工文件。**不会**再把处理不掉的格子算成封住了。
- **横带、贴着建筑、雷管够不到的地方交给镐子**：摆位时会同时盯着「这一发会不会打到东西」。严格级别下，只要存在一个不伤任何结构物/建材的摆位，就一定选它；如果某个封带格附近**所有**摆位都躲不开，那几格就不炸了，改成挖掘格写进施工文件。
- **接管前先盘点**：开工第一件事是数雷管（计划发数 + 余量）、看镐力（≥ 计划要求）、数封堵物块；任何一项不够就**拒绝接管**，状态里写清楚缺多少。半个隔离带比没有隔离带更糟，所以宁可不开工。

判据里的两张表（68 项「一镐就没」的 `tileNoFail`、398 项 `tileFrameImportant` 结构物）是从反编译源码里**生成**的，不是手抄的。感染物块（草/荆棘/藤蔓）即使属于结构物表也会被排除，因为它们是传播源本身，必须清掉。

## 进游戏按键接管（测试用）

`tools/make-test-copy.ps1` 会造一份**测试副本**：游戏本体复制一份、插件只装进副本、存档也是副本，进世界后按键接管。

```
pwsh -File tools/make-test-copy.ps1              # 默认 D:\zhadai-test，世界 草剑挥打
pwsh -File tools/make-test-copy.ps1 -SkipGameCopy  # 只更新存档/插件/计划
```

产物：

- `D:\zhadai-test\game`（副本游戏，已注入插件）、`D:\zhadai-test\save`（副本存档）
- `start-test.cmd`：双击启动。**工作目录必须是副本目录**，否则副本一闪而过（脚本已处理）
- `game\ZhaDai\run.cfg`：`plan=plan-quick.zplan`（40 发小样本）、`hotkey=F8`、`maxdeaths=50`
- `game\ZhaDai\plan.zplan`：整图（2,177 发）；想跑整图把 run.cfg 里的 plan 改一下，插件每秒重读

`run.cfg` 现在多两个键：`hotkey=F8`（进世界后按一下开始、再按一下停止）与原有的 `plan=`/`enabled=`/
`allowexplosives=`/`maxdeaths=`/`hostiledistance=`。带 `hotkey=` 时 `enabled=` 只在第一遍读到时生效，
之后由按键说话（否则每秒重读配置会把刚开的接管又关掉）。

按键状态来自 `Main.keyState`（`Terraria/Main.cs:973`），而游戏只在窗口有焦点时才填充它
（`Main.cs:18607`），所以失焦时不会误触发。死亡处理：记一次死亡、报位置、等复活、回到当前这一发继续，
超过 `maxdeaths` 才停（`BlastExecutor.HandleDeath`）。
## 藤蔓根：一块木头换掉一条竖井

带草的前沿物块会长出藤蔓，藤蔓按 `WorldGen.CheckVines` 继承上方物块的种类，于是腐化草长出来的是腐化藤蔓（636），而 636 自己就是传染源——这是唯一能绕过封带的自然通路，所以老版本要么按 `--vine-reach` 往下挖一条 13 格竖井，要么不保险。

现在默认改成**封堵**：在每个藤蔓根正下方那格放一块不可感染物块（默认木材），藤蔓没有可以起头的地方，整条竖井就不用挖了。

- 规划器算出封堵清单并写进施工文件 `#PLUG x y item=9`；`--no-plug` 退回挖竖井，`--plug-item=<id>` 换材料。
- 传播模型知道封堵块的存在：被封堵的藤蔓根不再算通路，所以复核依然说「全部封住」——这不是嘴上说说，是拿真实传播图跑出来的。
- 实测 草剑挥打：雷管 **10,535 → 9,452 发**（省 10%），封带 30,499 → 25,531 格，改挖 78 → 4 格，顶掉 38,727 格竖井，复核仍然全部封住。
- 执行器把封堵放在**最后**：放在爆破范围里的方块会被下一发炸掉，所以等所有雷管响完再填；届时那格还是石头就跳过（石头本来就挡藤蔓），放不下去就记 `PlugsSkipped` 并明说「这一格藤蔓根可能还在」。
- 接管前盘点把封堵方块算进去：不够就直接拒绝接管（`NotEnoughSupplies`），不会挖到一半才发现没带够。

## 它是怎么算的

1. **建图**：把所有「可被感染」的物块当成节点。原版硬模式扩散是 `WorldGen.hardUpdateWorld` 里一个 ±3（切比雪夫）的随机取点，**不检查邻接、也不检查视线**，所以隔着 2 格空气照样命中第 3 格；白名单只有 2/477、1/苔藓、53、396、397、60、69、161。
2. **封带 = 前沿的邻居集合**：把所有距感染前沿 ≤`clearance` 的可感染物块标为要炸掉。炸完这片全成空气，空气不在白名单里，前沿再也够不到任何节点。因此封带是**贴着轮廓**的一条带：前沿是斜的，带就是斜的，绝不是包围盒。
3. **不只是证明，还实测**：每个段都会用真实图跑一次泛洪，从前沿出发看能不能走出去。走不出去才标 `sealedByFloodVerification: true`。JSON 里另有 `allSectionsSealed`，CLI 的退出码也跟着它变。
4. **藤蔓单独处理**：`WorldGen.CheckVines` 会把藤蔓染成它上方物块的种类，所以腐化草长出来的就是腐化藤蔓（636），而 636 在 `SpreadsCorruption` 里，它自己就是传染源。带草的前沿物块下方必须是空的，藤蔓会顺着空气往下长，所以这类物块的整列要额外挖一条竖井封带，并在爆破碎片的另一侧留够余量。
5. **雷管摆位**：雷管破坏半径 7 格（`Projectile.Kill_ExplodeTiles`），严格圆盘，轴向实际只到第 6 格。摆位在候选窗口里搜「能掀掉最多未覆盖封带格」的位置，而不是见一格炸一格——后者会把一半半径浪费在感染那侧。

## 证据

一条命令跑完全部验证（ASCII 输出的脚本，PS 5.1 和 7 都能跑）：

```powershell
.\tools\verify-all.ps1              # 自动找 Terraria.exe；找不到就跳过注入相关的两步
```

它会依次：编译四个项目 → 跑测试 → 校验地图载荷 → 渲染并检查五个界面状态（像素统计证明不是空白）
→ 编译注入插件 → 拿插件里的成员清单核对真实 `Terraria.exe` → 在**副本**上演练注入并对比原文件哈希
→ `install --dry-run` 确认不落盘。本机结果：**8 步全部通过**。

`tests/ZhaDai.Core.Tests` 是一个不依赖测试框架的控制台程序，**103 条检查**：

```powershell
dotnet run --project tests/ZhaDai.Core.Tests -c Release -- "C:\Users\<你>\Documents\My Games\Terraria\Worlds"
```

- 物块分类、爆破几何、传播图（含「6 格空隙有效」「藤蔓 13 格能到、14 格到不了」）。
- 规划器自检：斜带确实沿对角线展开、两次规划结果一致、合并距离的取舍方向正确。
- 执行器在**模拟世界**里跑：干净场地跑完不自杀、起爆瞬间都在爆炸范围外、退不掉时确实会死但**死后不丢这一发**、复活后把墓碑挖掉、炸弹桶/岩浆/没撤离空间/没雷管/敌怪贴脸/快淹死各自走对应分支。
- 三张真实存档的集成测试：读出合法尺寸、规划结果全部通过泛洪复核。

## 接管执行

`src/ZhaDai.Automation` 是与游戏无关的执行器状态机（`netstandard2.0`），决策只通过 `IGameBridge` 读写世界，因此可以脱离游戏测试（上面那批模拟测试就是）。

`src/ZhaDai.Runtime` 是注入进游戏的插件（`net48 x86`），**编译期不引用任何游戏程序集**，全部按名字反射：

- 反射用到的每个游戏成员只在 `ReflectionRequirements` 里声明一次，缺了必需项就拒绝启动——一个对「哪里是实心的」「哪里有岩浆」判断错的执行器，比不启动更糟。
- 这份清单会被 `zhaodai-patcher verify` 直接读出来，逐项对着真实的 `Terraria.exe` 元数据核对。本机 1.4.5.8 的结果是 **62 项全部对上，必需缺失 0、可选缺失 0**。
- `src/ZhaDai.Patcher` 负责可逆注入：备份 + 哈希清单 + `File.Replace`，并提供 `verify` / `patch-copy` 这类**不用启动游戏**的离线校验命令。

前端和运行时之间没有输入钩子，全靠游戏目录下的文件往来，所以启停不需要热键、也不怕切出去：

| 文件 | 谁写 | 作用 |
| --- | --- | --- |
| `ZhaDai\active.zplan` | `zhaodai arm` / 管理器 | 施工文件，第 2 节那种格式 |
| `ZhaDai\run.cfg` | `zhaodai arm` / 管理器 | `enabled=` 开停，`plan=` 指向施工文件，另有 `allowExplosives`、`maxDeaths`、`hostileDistance` |
| `ZhaDai\status.txt` | 插件 | 每秒刷新：状态、第几发、已炸、跳过、死亡、清墓碑、当前提示 |
| `ZhaDai\runtime.log` | 插件 | 自检结果、每一次跳过与死亡的原因 |

> 现状要说清楚：执行器的决策逻辑是在模拟世界里验证过的，注入链路的**成员清单**是对着真实二进制核对过的；但**没有在本机真机跑过 Terraria 完成一次实际施工**。没有验证过的部分就是没有验证过，不要当成能用。插件写不出来状态文件时，先看 `runtime.log` 里的自检输出。


## 前端

`src/ZhaDai.Manager` 是一个亮色无边框的小窗口：选存档、调参数、看结果、打开交互地图。它用 `--ui-smoke` 在无显示环境下把各个界面状态渲染成 PNG，所以界面本身也是可回归的。

## 构建

需要 .NET SDK 8。`net48` 的两个项目（Patcher / Runtime）另外需要 VS2022 的 MSBuild 和 Mono.Cecil 0.11.6（放到 `lib/`，不随仓库分发）。

```powershell
dotnet build src/ZhaDai.Core -c Release
dotnet build src/ZhaDai.Automation -c Release
dotnet build src/ZhaDai.Cli -c Release
dotnet build src/ZhaDai.Manager -c Release
dotnet run  --project tests/ZhaDai.Core.Tests -c Release
```

## 已知限制

- 执行器的寻路是「朝目标直走、撞墙就挖」，不是完整的路径规划；遇到复杂地形会走得很笨，走不到就跳过并记原因，不会硬撑。
- 藤蔓向下能长多长在原版里是生长过程而不是常数，`--vine-reach` 是个保守设定；把带草的前沿物块本身炸掉才是彻底断根的做法（方案里会报 `vineAnchorTiles` 给你）。
- 一片已经被完全感染的世界（例如 `全员处刑`）本来就封不出小范围，方案会照实报出段数和炸药量，不会假装乐观。
- 只支持原版 1.4.5.8 存档（格式 269–326）。模组世界不保证。
